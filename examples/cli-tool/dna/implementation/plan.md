# Implementation Plan

> Auto-generated by the dna-spec skill from the DNA.

## Strategy

Vertical slice first. M1 ships a CLI that can read a `tk.toml`
and print the task list. M2 adds the runner. M3 adds the
visualization and dry-run.

## Build order rationale

Config parsing is the foundation. Without a valid config, the
graph and executor have nothing to operate on. The runner (M2) is
the product's reason to exist, so it follows immediately. UX
polish (graph, dry-run) is M3 because the user can already be
productive with `run` alone.

## Milestones

### M1: Foundation

**Goal**: A working CLI that parses `tk.toml`, validates it, and
prints the task list.

**Scope**:
- Domain(s): config
- Feature(s): init, list
- Flow(s) covered: first-run (partial)

**Depends on**: nothing

**Tasks**: T-001 .. T-004 (4 tasks)

**Exit criterion**:

- `tk --version` prints the version

### M2: Graph & Executor

**Goal**: Tasks can be run, in dependency order, with proper
failure handling.

**Scope**:
- Domain(s): graph, executor
- Feature(s): run
- Flow(s) covered: first-run, failed-task

**Depends on**: M1

**Tasks**: T-005 .. T-008 (4 tasks)

**Exit criterion**:
- `tk run <name>` runs the task and its deps in topological
  order
- A cycle in the graph produces a clear error
- A failing task stops the run and propagates the exit code
- Child processes are cleaned up on SIGINT

### M3: UX

**Goal**: Dry-run and graph visualization. Output is colored and

**Scope**:
- Domain(s): all

- Flow(s) covered: none new

**Depends on**: M2

**Tasks**: T-009 .. T-012 (4 tasks)

**Exit criterion**:

- `tk graph` prints the dependency tree

## Cross-cutting concerns

- **Error handling**: every error path must print a clear
  message and exit non-zero. Set up in M1.
- **Color output**: auto-detect TTY, set up in M1, used in M2
  and M3.
- **Tests**: integration tests run real `tk` against real
  configs. Set up in M1.
